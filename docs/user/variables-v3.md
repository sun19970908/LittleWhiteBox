# 变量 3.0

变量 3.0 把一张卡的玩法规则写进角色卡：有哪些数据、玩家能做什么、什么条件下发生什么，都由结算引擎按规则执行，模型只需要说“发生了什么”。从一个想法到一张能玩的卡，小白助手可以全程陪你做。还没决定用 2.0 还是 3.0，先看[变量系统总览](variables.md#选-20-还是-30)。

## 1. 从想法开始，不要求学习什么是3.0

你想做一张冒险卡：休息消耗补给，装备影响防御，委托完成后解锁商店。也许还没写下一个字，也没想好具体数值——把这个想法告诉小白助手，就能开始。

助手陪你把玩法补全：角色能做什么、需要什么条件、消耗什么、什么时候发生事件。然后在同一个卡片工作区里写角色设定、开场、世界书、变量开局值、规则和前端面板，接着检查规则、试算动作、按结果修改。试玩时发现问题，也回到这张卡继续改。

**助手就在酒馆里。** 它能直接看现场：读取聊天楼层里面板的实际 DOM 和 CSS 布局，翻插件日志，看你发来的截图，读当前聊天的真实变量，用当前进度试算一个动作。哪里显示错位、哪个按钮没反应、哪个数算得不对，它拿现场数据核对，再回到这张卡的草稿里改。这些不需要另外配置调试环境，打开助手就能用。

## 2. 写好一套玩法，多个地方直接使用

卡上的规则定义只写一份，同时用于：

- **更新模型**：可写字段、动作和参数直接生成提交工具，规则说明组装成更新资料；
- **正文模型**：世界书里的宏读出当前变量和相关玩法说明；
- **卡片面板**：商店、营地、装备界面上的按钮调用同一批动作，不必另写结算逻辑；
- **结算结果**：每处变化标明来自哪个动作、哪条规则。

作者改好一个动作，不需要再为更新模型另写一份协议、为正文另写一份说明、为面板另写一份计算。

规则和自定义函数保存在角色卡里，随卡分享；当前进度使用酒馆原生变量，随聊天保存。卡规定“怎么玩”，聊天记录“玩到哪里”。

## 3. 复杂玩法由程序执行，模型不用逐项算账

剧情里买下并穿上一件盔甲，更新模型只需提交作者定义的“购买并装备”。扣钱、入库、换装、重算防御和负重、达到条件后的触发，都由结算引擎按卡上的规则完成。

动作可以带参数、前提和多个效果；属性可以由其他字段算出，越界自动修正；条件达成自动触发后续。表达式写不下的，用隔离运行的 JavaScript 函数写，比如掷骰、战斗回合、多人按速度排序结算。玩法越复杂，模型漏算、重算的机会就越少。好感度这类需要理解剧情的变化，仍可交给模型判断。

## 4. 关联修改作为一个完整事件处理

一次结算里的直接改值、动作、关联计算、规则修正和条件触发按顺序一起算完，再检查最终的结构和约束。全部通过才写入；任何一步不通过，整批都不生效。买东西要么扣钱和给物品一起成功，要么一起不生效，不会出现“钱扣了、货没到”。

结算前可以试算，结算后能看清、能补救、能撤销：

- **试算**：制作时，助手用当前进度把动作先算一遍，看会怎样变化，不改聊天进度。试算和游玩时的结算是同一个引擎，试出来的就是玩起来的。
- **失败原因**：比如“购买 · 条件不成立：现金 102，需要 ≥ 297”。
- **变化来源**：结果弹窗分开显示动作本身、关联计算、规则修正和触发，以及模型写的剧情原因。
- **重试保存**：变量已改但保存未确认时，只重新保存，不会再扣一次钱。
- **撤销与回滚**：每个回复版本记下实际变化，切换回复、删除末尾楼层或撤销时直接恢复，不重新请求 AI。

## 开始使用

### 1. 选择 3.0，启用卡上的规则

打开 **扩展设置 → 小白X → 数据互动 → 变量控制**，勾选 `变量管理`，下拉框选择 **`3.0 · 卡规则与结算`**，再点旁边的 `变量更新` 按钮。

- **角色卡已经带有 3.0 规则**：新建聊天时会自动初始化；已有聊天在“当前聊天”页点击“启用规则”。
- **角色卡还没有规则**：先到“制作规则”页制作，不能只把模式切到 3.0 就让普通卡自动拥有玩法。

初始化会补齐缺少的变量根，并按卡上规则计算和检查。例如卡使用 `hero`，聊天里还没有它，就从开局值创建；已经存在的 `hero` 会作为起点检查，不会直接换成开局值。其他独立变量不受影响。

### 2. 看这张卡何时更新

“当前聊天”页顶部会显示卡作者选择的方式：

| 卡的方式 | 游玩时怎么发生 |
| --- | --- |
| 回复前更新 | 发出玩家消息后先结算，再生成正文。自动执行，不需要另开开关。 |
| 回复后更新 | 读完正文再更新。勾“回复后自动更新”就自动执行，否则点 AI 楼下的“更新变量”。 |
| 回复前＋回复后更新 | 先确定这次行动的结果，正文写完后再处理作者分给后置的变化。 |

前后阶段各自调用更新模型，会产生各自的 API 费用。更新模型可选小白助手的主助手 API 或分身 API；API 在[小白助手](assistant.md)里配置。没有回复后更新的卡，不会显示后置开关或更新按钮。

### 3. 查看结果与保存状态

楼下的“查看结果”打开弹窗，标题标明“回复前”或“回复后”，可以直接查看变化、保存状态和失败原因。“设置”回到当前聊天的更新设置。后置更新的主按钮会随状态变为“重新更新”“取消”或“重试保存”。

前置结果属于玩家发出的那条消息。停止正文、正文失败、重新生成或重新打开聊天，都复用已有的结果，不会重新掷骰、重复扣钱。改了这条玩家消息，楼下显示“消息已修改”，直接点“重新结算”按新内容计算，新结果替换旧结果。点“撤销结算”后也不会在下次生成时偷偷补算。

行动本身不满足条件，例如钱不够，会把失败原因交给正文演绎。请求失败或模型提交有误时，正文先停下来，玩家楼下提供“重试”和“跳过结算”。

**结算生效和保存成功是两件事。** 如果显示“结果已生效，但未确认保存”，当前变量已经改变，应点击“重试保存”。重试只保存已有结果，不会再次扣钱、发奖励或执行动作。

正常回复前结算会先把变量和记录交给酒馆，正文立即读取这些结果，随后随酒馆聊天一起保存，不在正文前额外等一次保存。手动操作、撤销和回复后更新仍会主动保存。

如果模型已经返回操作，只是本地计算环境故障，插件会换一个执行器再算一次，不重新请求模型。仍未完成时，点“重试结算”继续用这份操作计算；当前玩家消息尚无正文时，点酒馆“重新生成”也会复用它。只在当前页面保留这一笔待重试操作；成功、取消、切聊天，或消息、变量、规则变化后释放，刷新页面也会丢弃。

刷新或重新打开聊天后，如果玩家消息还没有前置结果，楼下会显示“未结算”，可以点“结算”重新请求更新模型，或“跳过结算”继续正文。已有的前置结果仍按原样复用。

## 制作自己的玩法

### 从玩法开始，而不是从一长串变量开始

先想清楚一次操作：什么条件下允许发生，发生后改变什么，能不能重复。例如“交付三份材料 → 完成委托 → 获得奖励 → 标记已领取”。再决定需要哪些字段。

变量适合保存**当前事实和玩法条件**：地点、资源、任务阶段、完成标记、次数、期限。剧情经过交给剧情总结，不必在变量里再存一份越来越长的事件日记。

“制作规则”页提供两种入口：点击“助手制卡”，按卡的玩法编写；或直接编辑规则文件。编辑后的三个操作分别是：

1. **检查规则**：检查草稿并计算开局状态，显示开局变量或具体错误，不修改聊天。
2. **保存草稿**：保留编辑内容，尚未替换角色卡上的规则。
3. **存入角色卡**：把规则和引用的函数保存到卡上，之后的结算使用这套规则。

检查通过表示定义和开局状态可用，不代表每条玩法路线都已经验证。制作后还需要试一次成功、一次条件不满足，以及重复操作、换装或跨过时间点等实际场景。

### 规则文件里分别写什么

主文件是 `variables/definition.json`，自定义函数放在 `variables/functions/`。这些是卡片工作区中的编辑文件，保存到角色卡后会随卡携带，不要求玩家安装同名本地文件。

| 内容 | 对应字段 | 用途 |
| --- | --- | --- |
| 何时更新 | `updates` | 回复前、回复后，或两者都用 |
| 变量结构与开局值 | `schema`、`initial` | 有哪些数据、类型和范围，开局是什么状态 |
| 字段含义与修改方式 | `access` | 谁能修改字段，模型应依据什么剧情更新 |
| 玩家能做的操作 | `actions` | 动作名称、参数、前提和产生的变化 |
| 自动计算与修正 | `rules` | 算出属性，或把超出范围的值修正回来 |
| 条件达成后的变化 | `triggers` | 到达时间、阶段或次数后发生什么 |
| 不允许出现的状态 | `constraints` | 检查多个字段之间是否互相矛盾 |
| 自定义计算 | `functions` | 用 JavaScript 编写较复杂的计算 |
| 给正文看的信息分组 | `views` | 按场景选取人物、装备等相关说明 |

变量使用 JSON 数据：文字、数字、布尔值、`null`、列表和对象。`initial` 的最外层是对象，各顶层字段对应原生聊天变量。3.0 首次启用时确定负责哪些顶层变量及其子字段；之后只在 `schema` 中增加声明，不会自动接管聊天里的其他独立变量。

动作的 `id` 用于程序提交，必填的 `title` 是结果和失败提示里显示的短名，`description` 是给模型看的完整说明。参数也可以写 `title`，让失败提示更容易看懂。

`updates` 必填。只选一个阶段时，动作和可直接修改的字段自动归到该阶段；同时选择 `before` 和 `after` 时，每个动作及允许 `direct` 的 `access` 项都需要写 `stages`。模型只拿到本阶段可提交的动作和字段，结算也按相同权限检查。**计算、修正、约束和触发只写一套，不分前后。**

选择阶段要看玩法需要，不是越多越好。掷骰、战斗、探索这类需要先知道结果再描写的完整行动适合放在回复前；依赖正文理解的关系变化适合回复后。若只是减一点血，通常直接放进已有动作或已有阶段，不值得为它单独多发一次请求。

完整的规则格式、营地示例（变量、动作、状态显示和面板按钮如何配合）以及卡片面板调用动作的接口，都内置在小白助手的制卡说明里。在“制作规则”页点“助手制卡”，直接问助手即可，例如“给我看营地示例的面板怎么调用动作”。

## 正文模型看什么，更新模型做什么

正文模型负责演绎，更新模型负责把剧情转成变量操作。两者需要知道同一套玩法事实，但不需要收到同样的操作指令。

启用回复前更新时，结算后的值先写入原生变量，本轮正文的世界书宏直接读到这些值。[剧情规划](ena-planner.md)的计划在玩家采用后才结算，再重新组装正文资料。

需要正文知道的前置结果会自动交给正文，不要求作者再放一个宏：

- 执行了动作，或变量有实际变化：交给正文；即使数值没变，已经执行的动作也会保留。
- 行动因条件不满足而未成立：把失败原因交给正文。
- 前置成功，但既没有动作也没有变量变化：不额外加入结算参考。跳过或撤销前置结算时也不加入。

这份参考只说明最新玩家消息中已经判定的部分，其余内容仍由正文演绎；前置没有变化，不代表正文发生后也没有变化。原始数据、字段路径和结果标签只是生成参考，不是要写进故事的内容。

前置记录会保存动作及其实际采用的完整参数，包括规则转换后的参数值。正文和回复后更新读取同一份已保存结果，知道做过什么、对谁做、用了多少，而不是只凭变量差异猜测；重新打开聊天或重新生成时也复用这份记录。

作者可以在正常启用的世界书条目中放入以下宏：

| 宏 | 展示内容 |
| --- | --- |
| `{{xbgetvar::hero.health}}` | 当前生命值；路径按自己的卡填写 |
| `{{xbgetvar::hero}}` | 整个 `hero` 对象的当前值 |
| `{{xbvardesc}}` | 卡中各视图的字段含义及相关玩法说明 |
| `{{xbvardesc::character}}` | 只展示 `views.character` 所涉及的说明 |

`character` 是护符示例里的视图名，**不是固定关键字**。卡里定义了什么视图，就使用什么名字。启用聊天后，应把世界书实际使用的宏展开一次，确认读到的是这张卡的字段。

描述宏包含相关的动作、计算、触发和约束说明，但不包含当前值或提交指令。需要当前值时搭配取值宏使用，也可以按世界书条件只发送当前场景需要的部分。

字段的 `description` 解释世界事实；`update` 解释什么时候更新、依据什么证据。后者只给更新模型。更新模型还会收到当前状态、结构要求、可写路径、动作参数和规则说明；它选择提交哪些变化，具体计算由引擎执行。

## 结算是怎样完成的

### 先计算和检查，再改变聊天

一次提交可以包含直接赋值 `set`、数值加减 `inc`、删除 `remove`，也可以包含卡上定义的动作。它们按顺序执行：前一项改过的值，会成为后一项的起点。`inc` 加减的是执行到这一步时的当前数字，不是本回合开始时的旧值；字段不存在或不是数字时会报错。

动作执行前会更新相关计算值，处理并检查参数，再检查前提。同一个动作中的多个效果读取同一份动作执行前状态，避免扣款顺序影响其他效果。动作执行后会再次计算、修正，并处理动作级触发；整批结束时处理批次级触发，最后检查完整状态。

结构检查使用 **JSON Schema**，负责类型、必填字段和范围等要求；跨字段关系由 `constraints` 检查。规则负责计算与修正，校验器负责判断最终结果是否合法。所有修改先在临时状态中完成，通过后才写回聊天；失败或提交前取消不会写入一半结果。

这条流程用于 3.0 的模型更新和卡侧 API。直接在原生变量面板改值不等于执行玩法动作，不会自动补做对应奖励和触发。

### 较复杂的计算：隔离运行的 JavaScript

表达式不方便描述的逻辑可以写成自定义函数，在隔离环境里运行。函数通过声明的路径读取数据，也可以读取本批修改前的值；不能访问酒馆页面、网络或存储。

这样，试算可以执行同样的计算，而不会顺手发送请求或改动页面。同一次结算复用计算线程，但每次函数调用的运行环境独立。函数以计算量和内存限制防止失控，触发链检查循环并设轮数上限；后台暂停或结果送达较慢不会被当成规则超时。取消或计算失败时，整批修改不生效。

普通比较条件失败时，结果可以显示字段名、实际值和要求值。自定义函数内部的判断不会被自动拆解，只能显示该函数判定不成立及其说明；函数说明需要把用途讲清楚。

## 切换回复、撤销与存档

### 恢复已有结果，不重新演一遍玩法

每个已结算的回复版本（swipe）保存自己的变化记录；前置记录保存在玩家楼。切换已有版本、从某楼删除到末尾或撤销结算时，3.0 根据记录恢复变量，不重新请求 AI，也不重新执行动作和奖励。取消正在生成的新版本时，会恢复原版本的变量。单独删除中间楼、隐藏或移动楼层不自动改写变量。

如果保留后面的楼层，只切换前面某一楼，后面已经结算的字段结果仍会保留，**不会按改写后的剧情重新推演后文**。例如后面已经开门，前面却换成了没拿钥匙的版本，恢复后就可能出现矛盾。

历史切换后会检查字段格式和卡上约束。没有冲突就不打扰；有冲突则显示规则和当前值，例如“开门必须持有钥匙：钥匙为无，门为已打开”。切换本身不会被阻止，程序也不会替玩家决定关门还是补钥匙。可以切回原版本，或通过后续操作解决冲突；下一批修改只要最终合法就能生效。

### 规则跟卡走，进度跟聊天走

- **角色卡**保存规则和自定义函数，随卡导出、分享。
- **聊天**保存当前变量（就是酒馆原生的聊天变量），3.0 另存恢复所需的变化记录。重新打开聊天使用已保存的进度，不重新开局。
- **导入／导出规则**只包含 `definition` 与 `functions`，不是聊天存档。导入会先检查、再确认，完整替换卡上的规则和函数，不清空当前变量，也不丢弃编辑草稿。已有草稿需重新读取卡上内容后再合并保存。

正在等待的模型更新如果遇到聊天、回复、当前变量或卡上规则变化，不会把旧结果覆盖到新状态上。结果已生效但保存未确认时，界面会单独提示重试保存。

数组按内容匹配，不要求你给每个元素额外加 id；有重复内容时按顺序配对。

保留后续楼层结果时，恢复会按需补回父结构。数组按位置恢复，必要的空位填 `null`；这不是按物品身份重新模拟库存。

恢复检查不会重新执行计算、修正或触发规则。依赖“修改前的值”的约束只在真正结算时检查。

模型提交时附带的剧情原因等说明只用于当次展示，不参与计算、不写入历史。数值变化或需要判断的变化建议附一句 `reason`，普通事实无需重复解释；`old` 只用于有必要的旧值比较，不必抄完整背包或日志。切换聊天、切换回复或撤销后，历史结果按保存的变化记录展示，不恢复旧说明。新增、删除的整块数据默认折叠，展开后查看字段；撤销的变化也默认折叠。

</details>

## 常见问题

### 正文已经写了结果，还会和变量不一样吗？

回复后更新不会回头改写已完成的正文。需要先确定数值再描写的玩法，可以由作者选择回复前更新，也可以由卡片按钮先执行动作，再把实际结果交给正文。正文拿到实际结果后仍由模型演绎，因此试玩时要核对叙述与结果是否一致。

### 保存新规则，会重置当前进度吗？

不会。之后的结算使用新规则，但保存规则本身不会重新计算现有进度，也不会重算历史楼层。因此，修改公式后，面板上的旧计算值可能保留到下一次结算；不要把“规则已保存”理解成“当前状态已按新规则全部更新”。

### 不同开场可以设置不同的初始值吗？

目前每张卡只有一份 `initial`，切换原生开场不会自动选择另一套初值。这是现有功能缺口。需要多开场不同状态时，要为这张卡另外实现开场选择与变量初始化的连接，不能只改问候语就当作已经完成。

### 支持群聊吗？

当前 3.0 按单张角色卡管理规则，尚不支持群聊。

### 需要让正文模型输出变量代码吗？

不需要。3.0 通过插件更新或卡侧 API 修改变量，不从聊天正文执行提交代码。正文可以专注叙事，无需插入专用的变量提交块。
