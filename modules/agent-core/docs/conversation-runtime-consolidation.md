# Agent loop 与会话历史管理收敛方案

状态：已暂停。用户决定暂不重构 agent-core，仅单独修正管理员的对话式工具历史和上下文管理。以下为暂停前的讨论记录与设想，不作为当前实施范围；其中管理员现状描述已由局部整改取代。

## 1. 目标与范围

Agent loop 与会话历史管理的通用机制归 `agent-core/runtime/`。按重复机制划定提取与迁移范围，不按三个 APP 的名单划界；每项已提取机制的真实重复消费者同步接入并删除旧算法。

用户可见的目标：管理员工具调用及结果跨回合保留；下一轮追问、重新打开会话和历史总结都能使用这些证据。模型请求、计量、压缩读取同一个上下文视图。

范围不包含：改变各 APP 的业务工具、重写供应商适配器、统一数据库、重做 UI，或改变后台维护提交、画图校验、课堂草稿和 RP 业务规则。这些功能仍属于共享能力的消费者和影响检查范围，不能因业务不同而排除依赖检查。

### 能力组合与会话结束边界

是否使用工具、是否跨用户回合保留历史，是两个独立维度。消费者按需组合共用能力，不强制调用一个大函数，也不据此新增四种运行器或 APP 模式开关。

| 使用形态 | 实际消费者 | 使用的公共能力 | 历史生命周期 |
| --- | --- | --- | --- |
| 无工具的持续对话 | 信息、四次元壁 | 模型请求 + 会话历史/上下文管理 | 跨用户回合保存，计量和总结使用有效历史；无需工具循环 |
| 一次性工具任务 | 画图场景规划、OS 地图/任务/世界维护、后台管理、委派子任务 | 工具执行与续轮 + 任务内上下文 | 整个任务内保留调用和结果；任务结束后不默认作为下一任务的聊天历史回放 |
| 带工具的持续对话 | 小白助手、ebook、管理员、小白酒馆管理助手、教育 APP | 工具循环 + 会话历史/上下文管理 | 每次回复结束后继续保留消息历史，包括工具调用和结果 |
| 无工具的单次生成 | OS 任务板等生成请求 | 模型请求及所需计量 | 使用该次请求的输入，不额外创建持久对话 |

“一次性工具任务”是一次完整运行，不是只调用一次工具或只请求一次模型；其中可以包含多次调用、结果反馈、纠错和模型续轮。画图规划结束也不等于图片已经生成，后续出图仍由画图工作流负责。

任务内上下文可以随整个任务结束释放，业务结果、提交记录及需要保留的诊断仍归原功能所有，不随之删除。再次运行由 APP 从当前事实构造输入，而不是自动继承上一任务的工具对话。

上下文管理独立于工具循环：计量、预算、摘要及覆盖边界的机制可以共享，APP 仍提供自己的背景组装、总结保留重点及业务消息分组规则。业务校验和事务编排可以保留自己的循环，但不再复制供应商续接和消息协议算法。实际调用依据见第 2 节。

## 3. 终态边界

```text
APP：会话存储、业务工具、Prompt、策略、权限与 UI
                  │ 明确的输入与回调
                  ▼
agent-core/runtime
  conversation：消息顺序、工具配对、回放与截断边界
  context：单一请求视图、计量、压缩候选及生效边界
  loop：请求 → 记录调用 → 执行 → 记录结果 → 续轮
                  │
                  ▼
已有 protocol / context-tokens / provider adapters
```

- core 不认识管理员、书库、任务、地图、课堂、DOM 或具体数据库，不反向 import APP。
- APP 提供会话读写入口、系统提示词和动态数据、工具定义与执行、预算策略及语义事件消费者。
- core 负责调用与结果的顺序、供应商会话续接、压缩后的会话重建、取消传播和错误上抛。APP 负责具体工具的授权、业务提交、未确认保存恢复和用户反馈。
- 执行机制与会话历史管理可以独立组合。一次性任务不必创建持久聊天；持久聊天不能因某次模型回复结束而失去工具历史。
- 存储成功是一个明确边界：需要持久保存的消息或摘要未确认时，不能被运行器当成已经保存并继续推进；恢复会话记录不能再次执行已有业务操作。
- 共用能力沿现有 ESM 和构建入口导出，不新增注册框架、依赖或全局单例。
- 提取收益必须可见：重复算法减少、APP 接入代码更短、状态更少，同一协议问题只修一处。若为接入而增加大量专用回调、APP 模式分支或适配层，说明提取边界过大，应缩小边界而不是继续补分支。

## 4. 唯一事实来源与生命周期

### 会话事实

用户消息、模型产生的文字、工具调用参数、工具结果及回放所需供应商 payload 归会话所有。最终回复、工具消息和 UI 正文不各存一份相同文本；页面从会话事实做有界投影。

回复结束不删除工具消息，这是统一会话契约，不是由每个 APP 选择是否遵守的保留策略。历史按压缩覆盖边界、显式删除和重新生成截断处理；完整会话的结束边界按第 1 节各使用形态确定。

业务保存回执仍表示实际业务提交状态，不替代工具原文，也不因历史回放而重新提交业务。未提交或失败的结果保留真实状态，不因写入历史变成已经生效。工具结果是当时观察，不是当前数据库的永久快照；需要最新状态时照常调用业务读取工具。

### 运行状态

取消信号、供应商 session、流式缓冲、待返回的 native tool responses、计量缓存只活在当前运行。它们释放时不能删除会话事实，也不作为下次重新生成的恢复队列。

### 上下文视图

从会话、有效摘要及覆盖边界构建一次请求视图。模型回放、请求前 token 计量和压缩选择都消费该视图；供应商使用原生 session 续轮时，计量仍覆盖整个已累积上下文。

界面显示当前有效上下文的估算，不混用“最后一次请求”和“重新打开后的下一次请求”两种口径。工具定义与工具结果分开归类；工具结果跨回合后仍计入历史，不能从总量中消失。保留现有计量来源标识，不把估算称为供应商精确用量。

### 持久化与删除

- 不新增 core 数据库、执行队列、锁或业务快照。会话及摘要由各 APP 的既有存储拥有，生命周期随该会话。
- 管理员必须将工具消息纳入既有会话存储，因为重开后仍需追问和总结；只放运行内内存不能满足该契约。
- 正式线助手与 ebook 的现行文件/数据库格式不因这次提取而改动。管理员使用一个当前模型，不保留旧 checkpoint 运行路径。
- 如管理员模型调整需转换现行文件，在读取/升级入口一次完成，保留文件中实际存在的对话、回执和附件；已被丢弃的工具原文不能重建或伪造。仅支持有实际样本的现行格式，不枚举测试线假想历史版本，不自动清空用户文件。
- 清空、删除、重新生成同步清理对应工具消息和受影响摘要；附件继续由 APP 的既有删除路径处理。删除管理员功能时，仍是删除其目录、注册及所属分区数据，core 不持有管理员记录。
- 存储失败沿用 APP 明确的未保存/冲突状态，旧已确认数据不被覆盖。后续重试只处理待保存记录，不恢复执行旧工具链。

## 5. 压缩与提示词

- 管理员预算以[应用策略](../../xiaobai-os/apps/administrator/domain/policy.ts#L2)为唯一来源；其他消费者沿各自现有策略，不统一数值。
- 通用流程负责计量、选择可压缩的完整消息组、取得候选、重新计量并应用覆盖边界。不能拆开调用与结果；当前未闭合的工具组不能压缩。
- 小白助手继续总结较早对话；ebook 继续按既有策略裁剪；管理员总结包括工具证据的较早交互。策略由 APP 显式提供，不在 core 判断 APP 名称。
- 管理员单轮过长时，允许总结当前轮已经闭合的较早工具组，保留当前请求及最新必要工具组。此摘要同样属于会话上下文，不能随当轮结束丢失。
- 总结失败或没有缩小上下文时，不把候选冒充成功压缩。助手已有显式本地摘要降级、ebook 的裁剪及各自超限行为作为 APP 策略保留，不给其他消费者增加相同分支。
- 有效上下文被替换后，由 core 重建供应商会话；回放消息不是重新执行工具。429 等请求失败不能顺便触发业务工具重跑。
- 身份、领域说明、工具 description、总结保留重点与原文引用安全规则留在所属 APP。core 不硬编码管理员身份或一份适用于所有业务的总结文案。
- `writing-model-prompts` 约束本次输入整理：只调整因新数据流而改变的事实，不顺带重写助手/ebook 的身份和工具指引。管理员总结输入使用真实会话消息，不再从 UI 回执拼出替代历史。

## 6. 实施顺序与旧代码退出

1. 对第 2 节消费者逐项建立“旧公共算法 → core 入口 → 接入点 → 退出代码 → 行为验证”的对应关系；保留业务编排和真实差异。先补当前检查覆盖不到的契约，不用源码字符串测试。
2. 先收敛消息协议与供应商续接，再收敛执行驱动和历史/上下文机制。复用现有消息协议、token 计数及适配器；不复制管理员循环然后改名，也不新造与现有协议并行的接口。
3. 每项机制提取时，将对应的真实重复消费者一起接入并移除旧算法；包括小白酒馆和画图使用的公共步骤。业务校验、权限、事务和 APP 数据/显示适配保留在原所有者，不留新旧开关或永久兼容包装。
4. 让持续会话遵守第 4 节统一历史契约，首先以管理员跨回合追问和重开场景验证。修正缺失工具历史及临时/持久两套事实重建；教育 APP 的课堂提交状态仍保留，小白酒馆的业务回滚边界不变。先前已修复的管理员重生成、输入框归属和保存 guard 必须保持。
5. 同步更新 core README 与相关设计文档的所有权说明，删除与实现冲突的旧说法；构建真实下游产物，执行第 7 节回归。

完成判据是公共机制具有唯一实现、对应消费者实际共用、被替代的旧算法退出，并验证会话契约和各业务边界。不是迁移满几个 APP，也不是把所有业务循环搬进 core。

## 7. 最少必要验证

| 契约 | 最便宜的验证层 |
| --- | --- |
| assistant 调用与 tool 结果配对、按顺序回放；中途取消不伪造未执行结果；错误不吞 | core 逻辑测试，复用供应商协议 fixture |
| 计量、总结、模型请求看到同一有效历史；原生 session 压缩后重建且工具只执行一次 | core 运行器测试，参数化覆盖原生续接与完整回放 |
| 当轮工具原文在下一轮及重开后可用；摘要覆盖后计量正确；当前轮摘要不会随收尾丢失 | 管理员存储/运行边界集成测试 |
| 重新生成删除选中 USER 后的旧工具链和错误，不带入旧 429；已提交业务不回滚或重做 | 管理员现有恢复/运行测试扩展 |
| 保存失败、停止、切聊和迟到回调不污染另一会话；确认保存不会恢复已停止执行 | 现有会话恢复测试 |
| 助手/ebook 原存储格式与原压缩策略保持 | 现有 session-store/history-compaction 和 ebook 测试 |
