# 小白X变量 2.0 制作

## 变量 2.0 适合什么卡

变量 2.0 保存当前的完整状态，删楼、swipe 时按楼层记录自动回滚。前端和模型随时读到最新的全部值，AI 每回合只交变化量，不重复输出全部状态。卡负责三件事：定义结构与初值、向模型提供状态与玩法事实并向更新执行者提供提交指令、让前端读取当前值。

它既可记录模型按剧情判断的变化，也可配合 `<varevent>`、玩法脚本和前端结算。变量 3.0（ReadSkill builtin-state3）提供内置的动作、派生值、修正与触发规则；需要这些内置结算能力时再选择 3.0，维修已有 2.0 卡沿用卡自己的玩法实现。

世界书的排布、开场白、正则、前端与循环任务按 ReadSkill builtin-card-files 组织；本技能只讲变量。

<a id="制作流程"></a>
## 制作流程

制作变量卡按以下顺序安排；接口和格式详见[变量指南](<references/xiaobaix-game-state.md>)。

1. **确定更新方式。** 新建或新增变量系统时，使用小白X独立变量更新：玩家点回复下的「更新变量」，或开启回复后自动更新；工具提交由更新器提供，不依赖用户的写作预设。正文 `<state>` 只在用户特别要求时使用，此时让剧情模型输出 `<state>` 并配隐藏正则。用户明确保留已有预设工具或玩法脚本结算时沿用它。只维修已有卡时保留原通道，不擅自迁移；同一变化只结算一次。
2. **先设计玩法状态。** 按下方“如何设计玩法状态”明确条件、后果、需要读写的状态、能否重复和执行者，再确定字段。
3. **设计条件触发与联动。** 从用户描述的玩法里找出“什么情况下会发生什么”：好感变化影响人物行为、收集条件达成后解锁内容、任务完成后执行结算、进入某状态后切换世界书或调用已有快捷回复。能由已有变量判断的条件，优先用世界书中的 `<varevent>` 组织。先读[条件规则与动作](<../../../card-workspace/skill/references/xiaobaix-capabilities.md#varevent>)，把触发条件、命中后提供给模型的内容、需要执行的动作，以及持续生效还是只执行一次一起设计出来。需要文字就写 `display`，需要确定执行的操作就写 `js_execute`，两者可以组合；用户描述玩法即可，不必指定标签名、JS 或工具。互斥规则和可同时发生的规则按参考中的选择方式拆分。
4. **建立初值与模型资料。** 角色任务初始化，世界书提供当前值、玩法事实与更新依据，具体分工见下方。

独立更新负责从正文判断变量变化；条件规则负责依据状态选择内容和执行确定的响应。脚本已结算的字段，在更新规则里交代归属，避免再让模型结算一次。只有数值记录的需求不额外造事件；需要即时按钮、定时或宿主事件响应时，按执行时机使用前端或循环任务，而不是把所有交互都塞进回合条件。

### 如何设计玩法状态

每个玩法先写成“条件 → 后果 → 需要读写的状态 → 能否再次触发 → 谁执行”。时间、事件、阶段和资源变化都要有对应的判断依据；已能从现有状态判断的条件直接使用它，不另建一份重复记录。

- 剧情经过、对话回顾交给剧情总结模块；变量保存会影响后续判断或展示的当前事实，例如任务完成标记、领取次数、当前阶段、期限。
- 事件需要在后续回合作为条件时，保存它留下的结果，例如“已获通行许可”，而不是逐回合追加事件全文。一次性奖励要能判断是否已领；持续效果要明确何时结束；周期事件要明确何时可以再次发生。
- 文本字段适合简短的当前目标、态度或关系事实；根据用途选择内容，不把文本一概禁掉，也不默认建立“大事记”数组。

### 初值、模型资料与前端

- **结构与初值**：在角色初始化任务中，用 `applyText()` 写入 `$schema`、约束和初始数据，初始数据必须写全模板字段。已有初始化先原位修改；多条开场白按变量指南分别处理初值。
- **区分玩法事实与提交指令**：剧情模型和更新模型都需要当前值、字段含义以及影响叙事的玩法事实；何时写哪个路径、怎样填写、如何提交属于更新执行者的指令。条目设置、宏与写法统一见[变量指南第 3 节](<references/xiaobaix-game-state.md#3-让模型看到当前值>)：
  - `{{xbgetvar::路径}}`：独立更新卡在世界书展示整块状态用它，对象输出 JSON；单个值嵌进句子也用它。其他通道的宏格式见变量指南。
  - 更新规则每条以提交时的完整路径开头（如 `西厢.人物.<人名>.态度`），只写何时改、怎么改。
  - 独立更新卡主动附上变量指南的“说明每次修改”段落与工具参数示例，让更新模型在每条操作里写 `reason`、按需写 `old`；示例路径换成卡里实际存在的字段。这是提示词要求，不是执行器的必填门槛。
  - 酒馆原生 `{{getvar::名}}` 只能取整个变量，读不到 `西厢.人物[0].姓名` 这类子路径，不用于变量 2.0 状态。
- **前端读取**：读当前值显示，不要求 AI 在正文里重复状态。

<a id="玩法验收"></a>
## 按这张卡的玩法验收

在隔离测试聊天里检查这张卡实际使用的机制；保存成功只代表文件已写回。

1. 初始化后核对开场值，在实际剧情请求和所选更新通道的请求里逐个核对用到的宏展开结果。空白时对照当前变量检查根名与完整路径，再查初始化和条目是否进入请求，不凭空归因为“变量不存在”。
2. 用同一条玩法分别试条件成立与不成立；有一次性奖励就试重复领取，有时间或次数条件就试跨过阈值，有装备或阶段变化就试变化后的下一次结算。
3. 实际走一轮“正文 → 更新 → 前端显示”，核对玩法依据、实际变化和最终值。脚本与模型共同参与时，同一变化只发生一次；正文与结算不一致时分别核对双方读到的状态、规则和执行结果，不能只凭其中一方认定另一方算错。
4. 切换 swipe、删楼、重新打开聊天后，核对当前状态与显示；有前端或任务时检查卸载与失败提示。直接结算的部分成功、规则修正与重读要求见[前端结算附录](<references/xiaobaix-game-state.md#frontend-settlement>)。
